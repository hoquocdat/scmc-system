# Design

## Context

See `proposal.md` for motivation and `specs/pos/checkout`, `specs/pos/shift-management` for required behavior. Current code that shapes the approach:

- `SalesService.create` (`backend/src/sales/sales.service.ts`) writes the order, items and **SALE inventory transactions at creation, for any status**. `SalesService.confirm` writes **SALE transactions again** and creates a `customer_receivables` row for the **full total**. The sales-order form calls create then confirm (`SalesOrderFormPage.tsx:85-87`), so confirmed orders currently deduct stock twice.
- `SalesService.addPayment` updates `payment_status` but never updates `customer_receivables`, so an order paid through it still shows as fully owed.
- `create` trusts `unit_price` and even `total_amount` from the client. Loyalty redemption runs **after** the transaction and its errors are swallowed.
- Order numbers come from `generate_sales_order_number()` = `COUNT(*) + 1` for today: concurrent inserts collide on the unique index, and deleting orders makes numbers reusable.
- Trigger `update_inventory_from_transaction` matches `product_id = NEW.product_id OR product_variant_id = NEW.product_variant_id`. A variant transaction that also carries `product_id` (as sales code writes it) also updates the base product's row. `inventory` has `CHECK (quantity_on_hand >= 0)`; when no inventory row exists, the update silently does nothing.
- Trigger `update_sales_order_totals` overwrites `sales_orders.subtotal` with the sum of line totals after every line insert.
- `pos_sessions` links to a **stock location**, while orders link to a **store** (`stores.default_warehouse_id` is the store's selling location). Users have no store assignment. `closeSession` computes expected cash from drawer movements only, ignoring sales.
- `PosController` uses role names `sales`/`manager`; `SalesController` uses `store_manager`/`sales_associate`. The CASL `PoliciesGuard` + `@CheckPolicies` pattern (used by service orders) already has subject `pos` with actions `create`, `read`, `void`.
- `POSPage.tsx` prices items as `sale_price || retail_price`, ignoring the sale-price dates and variant overrides.

## Goals / Non-Goals

**Goals:**
- One server endpoint that records a complete POS sale atomically and idempotently.
- Fix the existing sales-order defects that a POS sale would otherwise hit (double deduction, receivable on paid orders, order numbering, variant stock matching), in the shared code so the sales-order form benefits too.
- A single server-side price rule, which `price-books` later replaces.

**Non-Goals:**
- No cash-book entries (change `cash-book`); shift movements stay in `pos_session_transactions`.
- No reservations or negative-stock setting (change `inventory-operations`).
- No redesign of the sales-order status machine beyond allowing POS orders to be created directly as `completed`.

## Decisions

### D1. A POS sale is a sales order with `channel = 'pos'`, created as `completed`
POS orders reuse `sales_orders`, `sales_order_items`, `sales_order_payments`, receivables, loyalty and the reports by employee/channel. They skip draft/confirmed/processing/ready because goods leave the counter immediately.
- *Alternative*: a separate `pos_transactions` table. Rejected: duplicates stock, loyalty, receivable and reporting logic and creates two sources of sales revenue.

### D2. Extract an order-posting service shared by POS and sales orders
New `SalesPostingService` in `src/sales` with one method that, given a validated order draft and a Prisma transaction client, writes order, lines, payments, stock deductions, receivable and loyalty. `SalesService.confirm` and the new `PosCheckoutService` both call it. Rules inside it:
- **Stock is deducted exactly once, when an order becomes confirmed or is created as completed.** `create` of a draft no longer writes inventory transactions.
- **Receivable** = total − completed payments, created only if > 0; `addPayment` and refunds keep it in sync (same transaction). (The 017 trigger `update_customer_receivable` also syncs paid/balance on payment insert; the service recomputes explicitly so the rule does not depend on it.)
- **Subtotal trigger**: the 006 trigger `update_sales_order_totals` (which overwrote `subtotal` with Σ line totals) is dropped in migration 021; totals are written by the posting service only.
- **Loyalty** redeem/earn run inside the transaction. `LoyaltyService` methods gain an optional `tx` argument; a loyalty failure fails the checkout (spec: nothing recorded).
- *Alternative*: have `PosCheckoutService` call `create` → `confirm` → `addPayment`. Rejected: three transactions, not atomic, and it inherits the double deduction.

### D3. Endpoint: `POST /api/pos/checkout`
Request: `client_request_id` (UUID per checkout attempt, generated by the browser), `shift_id`, `customer_id` or `new_customer {name, phone}` or neither, `lines[] {product_id | product_variant_id, quantity, expected_unit_price, line_discount {type, value}}`, `order_discount {type, value}`, `points_to_redeem`, `payments[] {method, amount, amount_tendered?, reference?}`, `discount_approval_token?`, `notes`.
Response: the full order with lines, payments, store, cashier and loyalty result, which is all the receipt needs.
Errors: `409 PRICE_CHANGED` (with new prices), `409 INSUFFICIENT_STOCK` (product, available), `403 DISCOUNT_APPROVAL_REQUIRED`, `422` for payment/credit rule violations, `409 SHIFT_NOT_OPEN`.
Guarded by `JwtAuthGuard` + `PoliciesGuard`, `@CheckPolicies({ action: Create, subject: 'pos' })`.

### D4. Idempotency through `client_request_id`
`sales_orders.client_request_id` (nullable, unique). The POS keeps one id per cart until the server answers success. A retry with the same id returns the existing order with `200` instead of creating another. The id is regenerated only after the cart changes.
- *Alternative*: disable the button and hope. Rejected: does not cover timeouts where the server did commit.

### D5. Server-side price resolution (temporary rule)
`PriceResolver.resolve(item, at)`: variant `retail_price_override` if set, else product `retail_price` + variant `price_adjustment`; the product `sale_price` (or variant equivalent) applies only when `now` is inside its start/end dates. If `expected_unit_price` ≠ resolved price → `409 PRICE_CHANGED`. Totals are always recomputed on the server; client totals are not accepted. `price-books` replaces this resolver behind the same interface.

### D6. Stock check under row locks
Inside the transaction, lock the inventory rows for all lines at the store's `default_warehouse_id` (`SELECT … FOR UPDATE`, ordered by id to avoid deadlocks). Missing row or `quantity_on_hand < quantity` → `409 INSUFFICIENT_STOCK`. SALE transactions record `unit_cost` = current cost (variant `cost_price_override` or product `cost_price`), which lets `reports-fix-and-migrate` compute COGS at time of sale.
Trigger fix: match on `product_variant_id` when the transaction has one, otherwise on `product_id` with `product_variant_id IS NULL`.

### D7. Order numbers from a counter table
New table `document_counters (doc_type, period, last_value, PRIMARY KEY (doc_type, period))`. `generate_sales_order_number()` does `INSERT … ON CONFLICT DO UPDATE SET last_value = last_value + 1 RETURNING last_value` for `('SO', 'YYYYMMDD')`. Format stays `SO-YYYYMMDD-NNNN`. The row lock serialises concurrent numbering, values are never decremented, so numbers are never reused. The migration seeds today's counter from existing orders. Later changes reuse the table (returns, transfers, vouchers).
- *Alternative*: one global Postgres sequence. Rejected: loses the daily format staff already know.

### D8. Shifts are per user and store
`pos_sessions` gains `store_id` (backfilled from `stores.default_warehouse_id = location_id`) and `closed_by`; `location_id` stays as the store's selling location. A partial unique index `(user_id) WHERE status = 'open'` enforces one open shift per user. `sales_orders.pos_session_id` links each POS sale. The cashier picks the store when opening a shift (users have no home store); the last choice is remembered on the device.
Expected cash = opening + Σ cash payment `amount` in the shift (already net of change) + cash_in − cash_out. `GET /api/pos/shifts/current` returns the caller's open shift for resuming. Existing session endpoints are renamed to "shifts" in the UI only; API paths stay.

### D9. Permissions and discount approval
New permission rows (migration) on subject `pos`: `create` (sell, open/close own shift), `approve` (approve discounts), `credit` (sell on credit), `supervise` (view/close others' shifts; named `supervise` rather than `manage` because CASL treats `manage` as "every action"), `reprint`. Controllers switch from `RolesGuard` to `PoliciesGuard`. Role discount limit: new column `roles.max_discount_percent` (null = no limit).
Approval above the limit: the POS shows an approval dialog where a user with `pos:approve` signs in with their own account (a separate, non-persisted Supabase session on the device, since the backend has no passwords: authentication is Supabase JWT). The approver's token calls `POST /api/pos/discount-approvals`, which returns a short-lived HMAC-signed token (5 minutes) bound to the `client_request_id` and the approved percentage. Checkout verifies it and records `discount_approved_by`.
- *Alternative*: a manager approves from their own device. Rejected for now: needs live notifications for a 2-branch store where the manager is usually present.

### D10. Frontend structure
`pages/pos/POSPage.tsx` becomes a thin layout (<150 lines) over `components/pos/`: `PosShiftGate` (open/resume shift), `CartTabs`, `ProductSearch` (scan + search), `CartLines`, `CartSummary`, `PaymentSheet` (replaces the three payment dialogs with one split-payment form), `ApprovalDialog`, `ShiftSheet` (cash in/out, close, summary), `ReceiptDialog`.
- Server state through TanStack Query: `['pos','shift','current']`, `['pos','products', storeId, search]` (includes available stock), `['customers', phone]`; checkout is a `useMutation` that invalidates products, shift summary and customer.
- Carts are client state persisted in `localStorage` under `pos:carts:<userId>:<storeId>`, wrapped in try/catch.
- Keyboard shortcuts through one hook: F2 search, F4 customer, F9 pay, Ctrl+Enter complete, Ctrl+T new tab, Ctrl+1…9 switch tab.
- Scanner input is treated as fast keyboard input ending in Enter in the search box; an exact SKU/barcode match adds directly. (The barcode column arrives in `inventory-operations`; until then SKU is matched.)
- Offline: show a banner when `navigator.onLine` is false or a checkout fails with a network error; never clear the cart on error.

### D11. Receipts
Receipt data comes from the checkout response or `GET /api/sales/:id`, not from client state. Printing uses browser print with an 80 mm print stylesheet; A4 is selected by a setting. A reprint shows "BẢN IN LẠI" and writes an activity-log entry.

## Risks / Trade-offs

- [Existing stock levels are already wrong because of the double deduction and the variant trigger] → After deployment, run a stock count per location (first use of `inventory-operations`), or a one-off reconciliation script that recomputes `quantity_on_hand` from `inventory_transactions`; decide before go-live.
- [Changing when drafts deduct stock alters the sales-order form's behavior] → Same visible result for confirmed orders (deducted once); drafts no longer hold stock, which is correct until reservations exist. Covered by tests on both paths.
- [Loyalty inside the transaction makes checkout fail if loyalty misbehaves] → Required by the spec; loyalty methods are covered by tests; error message names loyalty as the cause.
- [Row locks on hot products during busy periods] → Transactions are short (single round trip, no external calls); ordered locking avoids deadlocks.
- [Password entry for approval on a shared screen] → Masked input, token bound to one cart, rate-limited endpoint, logged.
- [`update_sales_order_totals` trigger overwrites `subtotal`] → Posting service writes lines first and sets totals last, or the trigger is dropped in this migration; decided at implementation with a test that the stored subtotal equals the server's computed subtotal.

## Migration Plan

1. `backend/prisma/migrations/021_pos_checkout_core.sql`: `document_counters` + new `generate_sales_order_number()`; `sales_orders.pos_session_id`, `client_request_id` (unique), `discount_approved_by`; `pos_sessions.store_id` (backfill), `closed_by`, partial unique open index; `roles.max_discount_percent`; new `permissions` rows and default grants (sales associate: create; store manager: all); corrected inventory trigger.
2. `npx prisma db pull && npx prisma generate`.
3. Deploy backend, then frontend. Old POS page had no persisted data, so there is nothing to migrate on the client.
4. Rollback: the migration is additive except the two replaced functions; a down script restores the previous function bodies. Orders created by the new endpoint remain valid sales orders.
